# Codex в Docker

Каталог соответствует сервису `codex` в Compose. Образ собирает Codex из
исходников внутри Docker; предварительно компилировать программу на хосте или
класть её в `bin` не требуется.

## Что собирается

Исходники берутся из `https://github.com/openai/codex.git` по полному SHA
`727283cea5ba30e8cf8bbac6b68a03a4d91cf1b7`. Это ревизия ранее использованной
лабораторной сборки `home-session-stock`. Сборка использует Rust 1.95.0,
`Cargo.lock` и `cargo build --locked --release`.

В отдельной стадии собираются `codex` и `codex-code-mode-host`. Для второго
используется штатный Python-модуль выбранной ревизии, который скачивает
подготовленные V8-артефакты и проверяет их контрольные суммы. Сам V8 здесь
не компилируется из исходников. В итоговый Debian Bookworm образ попадают
обе программы после `strip` и системные библиотеки; Rust, исходники и `target`
остаются в сборочной стадии и кеше.

Code Mode требует второй программы рядом с Codex. Её наличие не включает
Code Mode в профиле автоматически. Текущий минимальный профиль его отключает.
Для иных инструментов могут понадобиться дополнительные программы в runtime;
этот образ не является универсальной средой разработки для всех проектов.

## Первая установка

Нужны Docker с BuildKit, Docker Compose v2, доступ к Docker Hub, GitHub,
реестру Cargo и достаточное место для компиляции. Лабораторный `target` на
момент проверки занимал 9,4 ГБ; это не верхняя граница. Дополнительно нужны
место для исходников, образов, V8 и конечных программ, а также память для Rust
и линковщика. На хосте Rust и Cargo не нужны.

Все команды ниже выполняются из корня репозитория сайта.
Настройте `docker/.env` по `docker/.env.example`, в частности уникальный
`COMPOSE_PROJECT_NAME`, `VITE_CHAT_AGENT=codex` и:

```dotenv
CODEX_IMAGE=local/codex:727283cea5ba30e8cf8bbac6b68a03a4d91cf1b7-r1
CODEX_REVISION=727283cea5ba30e8cf8bbac6b68a03a4d91cf1b7
CODEX_HOME_PATH=./codex/home/default
```

`CODEX_HOME_PATH` — путь на хосте относительно `docker/` либо абсолютный путь.
`docker/codex/home/` содержит отдельные профили: `default/`, `openrouter/` и другие.
По умолчанию монтируется только профиль `default/`, а не общий каталог профилей.
Путь внутри контейнеров остаётся `/codex/home`.
Подготовьте в нём отдельный профиль проекта:

- `config.toml` — настройки проверенной ревизии, провайдера и возможностей;
- `model-catalog.json` — каталог моделей, если он указан в конфигурации;
- `auth.json` — действующие учётные данные соответствующего аккаунта;
- `transport-token` — отдельный случайный токен WebSocket для этого проекта;
- `website-sessions/` — доступный на запись каталог связей посетителей с сессиями.

Профиль не создаётся при сборке образа. Для нового проекта используйте
проверенный профиль из лаборатории `codex-chatgpt.ru/codex-lab/projects`,
согласовав настройки модели и инструментов. Не копируйте историю чужого проекта.
У существующей установки каталог `home` сохранён при переименовании.
Авторизация, скопированная из другого профиля, не синхронизируется с ним.

Для нового home, в котором ещё нет transport-token:

```sh
mkdir -p docker/codex/home/default/website-sessions
(umask 077; set -C; openssl rand -hex 32 > docker/codex/home/default/transport-token)
```

Команда откажется перезаписывать существующий токен. Не меняйте его независимо
от клиентов. Приложение и Codex монтируют один home в `/codex/home`, поэтому
читают один и тот же файл. Права должны позволять обоим процессам читать
настройки и токен и записывать свои данные. Home исключён из Git, контекста
сборки, форматирования и раздачи через Vite.

Соберите образ один раз и запустите сервис:

```sh
docker compose --env-file docker/.env -f docker/compose.yaml build codex
docker compose --env-file docker/.env -f docker/compose.yaml -f docker/compose.prod.yaml up -d --no-build --no-deps codex
```

После настройки `VITE_CHAT_AGENT=codex` пересоберите frontend и перезапустите
приложение штатным способом проекта. Сам запуск Codex режим виджета не меняет.

## Несколько проектов

Задайте одинаковый `CODEX_IMAGE` во всех проектах на одном Docker-хосте.
Сборка одного проекта создаёт образ с этим общим тегом; остальные запускаются
с `--no-build`. У каждого проекта должны быть собственные `COMPOSE_PROJECT_NAME`
и home. Слои образа общие, контейнеры и данные отдельных проектов независимы.
Образ не содержит credentials, transport-token или историю.

В Compose используется `pull_policy: never`: локальный образ собирается явно,
попыток скачать `local/codex` из Docker Hub нет. На другом сервере либо соберите
ту же ревизию, либо перенесите готовый образ через `docker save` / `docker load`.
При использовании собственного registry задайте его имя в `CODEX_IMAGE` и
предварительно выполните `docker pull` на целевом сервере.

Не перезаписывайте прежний тег новой ревизией. Меняйте `CODEX_REVISION` и
`CODEX_IMAGE` вместе. При изменении Dockerfile или сборочного скрипта увеличивайте
суффикс тега (`r1`, `r2`, …), даже если SHA Codex остался прежним. Тег сам по себе
не проверяет соответствие содержимого SHA. Ревизия записывается в OCI label
`org.opencontainers.image.revision`. При обновлении проверяйте совместимость
профиля, протокола app-server, Rust toolchain и Python-модулей сборки.

## Общий кеш сборки

BuildKit сохраняет отдельно:

- скачанные registry- и Git-зависимости Cargo;
- V8-артефакты с разделением по архитектуре;
- `target` с разделением по Debian Bookworm, Rust 1.95.0 и архитектуре.

Идентификаторы кешей не содержат имя Compose-проекта: разные проекты на одном
builder используют их повторно. Для параллельных сборок задано `sharing=locked`.
Компиляция и копирование результата в `/out` идут в одном `RUN`, пока блокировка
ещё удерживается. Следующая сборка не может подменить бинарник перед копированием.

При неизменных входных файлах Docker может повторно использовать весь слой.
Когда слой приходится пересобирать, Cargo использует подходящие артефакты из
кеша `target`. Изменение features, компилятора или зависимостей может потребовать
перекомпиляции. При смене toolchain или базовой системы обновляйте также ID кеша
`target` в Dockerfile.

Кеш ограничен конкретным BuildKit builder. Другой builder или сервер не получает
его автоматически; одинакового `id` для этого недостаточно. Очистка кеша Docker
может удалить эти данные. Сборка должна работать и с пустым кешем. Экспорт кеша
слоёв не следует считать переносом содержимого cache mounts.

Существующий лабораторный `codex-lab/target` не подключается: он создан в другой
среде. Первая контейнерная сборка заполнит отдельный кеш, поэтому сначала расход
диска увеличится. Старые лабораторные файлы автоматически не удаляются.
Сохранённый при переименовании `bin/` тоже больше не участвует в сборке.

## Подключение и проверка

Внутри Compose приложение обращается к
`ws://${COMPOSE_PROJECT_NAME}-codex-1:4500` — полному имени контейнера.
Production-конфигурация не публикует этот порт на хосте. Для разработки добавьте
`-f docker/compose.dev.yaml`: порт публикуется только на `127.0.0.1`, по умолчанию 14500. Для нескольких проектов на хосте задайте разные `CODEX_PORT`.

Для приложения, запущенного на хосте, в корневом `.env`:

```dotenv
CODEX_SERVER_URL=ws://127.0.0.1:14500
CODEX_TRANSPORT_TOKEN_FILE=docker/codex/home/default/transport-token
CODEX_SESSION_DIRECTORY=docker/codex/home/default/website-sessions
```

После переноса home пересоздайте существующие контейнеры: изменение пути в
Compose не меняет mount уже работающего контейнера.

```sh
docker compose --env-file docker/.env -f docker/compose.yaml config --quiet
docker compose --env-file docker/.env -f docker/compose.yaml run --rm --no-deps --entrypoint codex codex --version
docker compose --env-file docker/.env -f docker/compose.yaml logs --tail=50 codex
```

Dockerfile проверяет запуск `codex --version`, наличие host-программы и отсутствие
неразрешённых динамических библиотек. Это не проверка авторизации или полноценного
диалога. После запуска проверьте ответ в виджете и возобновление диалога; если
включаете Code Mode, отдельно проверьте выполнение его инструмента.

## Статус проверки

21 ноября 2026 года проверена полная сборка на Linux amd64 с основным и dev
конфигами:

```sh
docker compose --env-file docker/.env -f docker/compose.yaml -f docker/compose.dev.yaml build codex app
VITE_CHAT_AGENT=codex docker compose --env-file docker/.env -f docker/compose.yaml -f docker/compose.dev.yaml up -d --no-build app codex varnish traefik
```

Первая стадия Cargo заняла 19 минут 13 секунд, включая загрузку зависимостей
в пустой кеш. Хотя V8 используется готовый, Cargo всё равно загружает Git-подмодули
его зависимости; первая загрузка заняла существенную часть времени. Во время
финальной оптимизации процесс Rust использовал около 26 ГБ RAM. Это измерение
конкретного запуска, а не гарантированный минимум или верхняя граница.
Итоговый образ занимает 467 362 603 байта (около 446 МиБ).

Проверено:

- `codex --version`, запуск `codex-code-mode-host --help`, динамические библиотеки;
- `readyz` и `healthz` возвращают 200; WebSocket без токена отклоняется с 401;
- страница и выдача токена доступны напрямую на `127.0.0.1:3001` и через
  прокси на `127.0.0.1:8080`;
- API отклоняет запрос без токена (401) и пустое сообщение (400);
- реальный ответ модели, SSE и продолжение диалога через прокси;
- сохранение контекста диалога после `docker restart` контейнера Codex;
- открытие виджета и реальный ответ в Chromium без ошибок JavaScript;
- повторная сборка Codex с `-p website_template_cachecheck`: сборочные слои,
  включая Cargo, получили `CACHED`, файловые слои образов совпали;
- `npm run types`, `npm run lint`, существующие тесты адаптера Codex
  (2 файла, 3 теста), конфигурации Compose и `docker build --check`.

Переиспользование всего слоя между проектами подтверждено. Ускорение Cargo при
изменённых исходниках и одновременные сборки отдельно не измерялись. Code Mode
в профиле отключён: проверен запуск host-программы, но не выполнение его инструмента.
Production-образ сайта и остальные сервисы стека в эту runtime-проверку не входили.

При проверке режим `codex` передан через окружение команды. Сохранённый
`VITE_CHAT_AGENT` в `docker/.env` не менялся: следующий запуск без override
использует значение из файла. Compose также предупреждает, что существующая
сеть `haih-monitoring-dev` создана другим проектом; настройки этой сети не менялись.

## Настройка через home

Команда запуска Codex одинакова для разных профилей. Модель, провайдер, URL API,
инструменты и остальные возможности настраиваются в `config.toml` выбранного
home. Переопределения через `command`, отдельный Compose-файл и пересборка образа
для смены этих настроек не нужны.

Выберите home в игнорируемом `docker/.env`. Например:

```dotenv
CODEX_HOME_PATH=./codex/home/openrouter
```

Путь задаётся относительно `docker/`. Храните локальные профили внутри
`docker/codex/home/`: этот каталог исключён из Git, форматирования и раздачи Vite.
Для нового профиля подготовьте `config.toml`, собственный `transport-token` и
каталог `website-sessions/` по инструкции первой установки. Не копируйте чужую
историю или авторизацию ChatGPT в профиль API-провайдера.

### Пример OpenRouter

В `config.toml` нового home сохраните ограничения инструментов минимального
профиля. Замените верхнеуровневые `model` и `model_provider`, уберите ссылку на
каталог моделей ChatGPT и настройку `model_reasoning_effort`, если они не подходят
выбранной модели. Добавьте настройки провайдера:

```toml
# Верхнеуровневые настройки должны находиться перед секциями [таблиц].
model = "google/gemini-3.1-flash-lite-preview"
model_provider = "openrouter"

[model_providers.openrouter]
name = "OpenRouter"
base_url = "https://openrouter.ai/api/v1"
env_key = "CHAT_API_KEY"
wire_api = "responses"
requires_openai_auth = false
supports_websockets = false
```

Это пример настроек провайдера, а не полный минимальный профиль. Возможности и
параметры модели должны поддерживаться выбранным API и используемой сборкой Codex.

Сам ключ задайте в игнорируемом `.env`. Основной Compose передаёт только
`CHAT_API_KEY` в окружение контейнера; Codex читает его через `env_key`.
Для профиля с авторизацией ChatGPT эта переменная не требуется. `CHAT_MODEL` и
`CHAT_API_BASE_URL` не управляют Codex: модель и URL он берёт из своего home.
Значение ключа не нужно записывать в `config.toml`, Compose или README.

Для приложения на хосте задайте в корневом `.env` пути к тому же профилю:

```dotenv
VITE_CHAT_AGENT=codex
CODEX_SERVER_URL=ws://127.0.0.1:14500
CODEX_TRANSPORT_TOKEN_FILE=docker/codex/home/openrouter/transport-token
CODEX_SESSION_DIRECTORY=docker/codex/home/openrouter/website-sessions
```

Запуск из корня проекта, без дополнительного Compose-файла:

```sh
docker compose --env-file .env --env-file docker/.env -f docker/compose.yaml -f docker/compose.dev.yaml up -d --no-build --no-deps codex
PORT=3001 npm run dev
```

Compose читает оба файла: при совпадении переменных `docker/.env` имеет приоритет
над корневым `.env`, даже если значение пустое. Переменные окружения shell имеют
приоритет над обоими файлами. Держите ключ в одном выбранном месте.
Приложение запускается на хосте и читает корневой `.env`.

После изменения `config.toml` перезапустите Codex:

```sh
docker compose --env-file .env --env-file docker/.env -f docker/compose.yaml -f docker/compose.dev.yaml restart codex
```

После изменения ключа или `CODEX_HOME_PATH` повторите команду `up` выше:
перезапуск сам по себе не обновляет окружение и mount контейнера. При смене home
обновите пути приложения и перезапустите `npm run dev`. Для проверки другой модели
начните новый диалог: существующие сессии могут сохранять прежние настройки.

21 ноября 2026 года проверены реальные ответы Gemini через `/api/codex`,
продолжение диалога с сохранением контекста и потоковая выдача SSE. Использован
существующий образ Codex без пересборки; код чата сайта не менялся.
